# Proposed integration plan

This is a staged replacement strategy, not permission to change code in this documentation phase. Keep existing presentation/routes and exact shared messaging/review contracts. Backend APIs in [api-contract.md](api-contract.md) are proposals requiring approval.

## Cross-cutting requirements before first cutover

1. Agree endpoint/DTO/error/version conventions, IDs, server sessions, deployment origins and database ownership constraints.
2. Introduce explicit asynchronous adapters/loading/error/query state at existing client seams. Current stores, resolver injection, hooks and useSyncExternalStore snapshots are synchronous. Do not drop a Promise into `current()`, `view()`, catalog arrays or messaging resolver methods. Keep server reads authoritative, UI rendering predictable and cancellation/account-switch races guarded.
3. Cache keys include authenticated account and role/context. On logout, expiry or switch, cancel outstanding reads, clear private cached data/drafts/retry state and prevent late responses from repopulating another account. Counts on error show unavailable, not zero.
4. Pick one authority per integrated module. No dual localStorage/server writes, no fallback creating local bookings/messages when network fails. Flagged rollout must not split one user's order across authorities.
5. Design transactional events/outbox and idempotency early, before booking integration. Reserve cancellation/payment behavior until approved. Establish staging fixtures through trusted test setup only, not production UI backdoors.
6. Back up server data using deployment procedures; demo export/import, if approved, is explicit/quarantined and validated. Never import browser passwords, permissions, Paid flags or ownership claims as trusted truth.

## API/data migration discipline

- Proposed `/api/v1` version covers network contracts, not the demo storage envelope version. A version-1 browser record is not automatically a valid database row.
- Decide discard vs opt-in sanitized import. Defaults should be no silent import. If importing: validate each record, map IDs consistently across users/profiles/services/bookings/chat/reviews, preserve snapshots, quarantine invalid references, never fabricate owners/payment/permissions, and publish an import report. Require real account credential setup separately.
- Canonical snake_case network DTOs need an explicit mapping layer for existing camelCase UI fields. Tests must compare semantic fields and ownership, not just successful status codes. Do not add aliases to exact Messaging contracts.
- Request metadata/idempotency and database outbox are internal infrastructure. Never expose credential records, private buyer location or internal dedup payloads to public consumers.
- Nullability: legacy createdAt unavailable is not today; review updated_at optional stays absent until edit; general vs service vs booking conversation nulls remain distinct. Empty optional date/address in demo maps to nullable server values and controlled form defaults.
- Pagination means visible array length is no longer total count; use server totals/aggregate endpoints and stable cursors. Sorting verified ratings must use aggregate dataset, not only current page.
- Backend timezone normalization must retain requested date semantics and disclosed trend window; don't convert local planning slots to UTC without seller timezone policy.

## Required acceptance evidence

Keep current isolated store regressions as behavior specifications. Add backend contract tests and real API end-to-end tests for foreign IDs, missing seller owner, stale revisions, duplicate concurrent requests/reviews/conversations, service-delete vs booking race, notification replay, storage/network outage, logout/account-switch stale response and public/private field exclusions. No passing frontend mock test proves server authorization or GPS success.

Run npm lint/build/test and diff checks after each adapter phase. Capture actual browser/device/version for Safari permission, dropdown and mobile keyboard testing; mark unavailable cases NOT TESTED. Preserve all existing Customer/Seller/Admin routes and visual layout. Do not integrate payments merely to make a demo review flow easy.
